# 我们把婚礼现场修图做成了桌面软件，安装包差点变成几 GB

做活动摄影的人，现场要出片。网一抖、图一上云，整场就停。所以我们把修图放在摄影师自己的电脑上：界面用 Electron，重活交给本机原生模块。

这不是又一个「用网页包一层」的工具。难的是三件事同时成立：预览要跟手、成片要稳、安装包用户能装上。下面是我们真实踩过的坑。

## 体积：不该进包的东西进了包

第一次打完整安装包时，体积大得不像给客户的东西。原因很土：构建目录、评测图、中间产物被打包配置收进去了。打包工具不会替你判断「这是垃圾」。

后来改成白名单：只带运行时真正要的壳、原生模块和资源。评测集、构建缓存、训练产物一律排除。体积立刻回到能发官网的量级。

教训就一句：**默认打包会把你开发时的脏东西一并带走，要自己写「只准带这些」。**

## 签名：漏掉的不是主程序，是旁边那个小东西

Mac 上主程序签了，系统仍可能不认。失败日志指向的，往往是崩溃上报、自动更新之类的辅助可执行文件，或者构建系统留下的半成品。

处理顺序必须由内向外：先处理嵌套的可执行文件，再签外层。签完用系统自带的校验，不要只看打包工具报成功。

Windows 我们没有买代码签名。现网安装包会碰到 SmartScreen，用户走「更多信息 → 仍要运行」。这是产品选择。

## 原生模块：压缩包里的库，加载器够不着

原生模块和它依赖的动态库，如果被封在资源归档里，运行时加载会失败。该解出来的路径要在打包配置里写明白。

有一次窗口标题在、内容全白，就是预加载脚本路径和归档布局对不上。原生库必须能被操作系统的加载器看见，不能只存在于压缩包的逻辑路径里。

## 现场：像素不上云

婚礼现场可能断网几小时。授权可以短时向服务器要许可，图必须继续在本机算。我们不把安全做成「每张图都上传」。

短时离线能出片，这是现场软件的底线。

## 开源的是零件，不是整套产品

修图引擎、模型和风格配方仍是产品本身。我们把用得上、又成不了竞品的一层单独开出来了：标准 Adobe `.cube` 读写、线性混合，以及教科书级的曝光 / 色温。

```bash
npm install liangzai-cube-kit
```

```ts
import { applyBasicGradeToRgba8, parseCube, applyCubeToRgba8 } from 'liangzai-cube-kit'

const graded = applyBasicGradeToRgba8(rgba8, { ev: 0.3, kelvin: 5200 })
const pixels = applyCubeToRgba8(parseCube(cubeText), graded, 0.8)
```
